## 3. Порядок работ

**Начинать с фазы 0.** Она почти ничего не стоит, ничего не ломает и определяет, имеет ли смысл всё
остальное. Никакую оптимизацию нельзя ни принять, ни отвергнуть, пока нет её измерений.

| Фаза | Что | Требует живого CH | Ломает тесты |
|---|---|---|---|
| **0** | Измерение: вернуть `elapsed_ns`, раздельные счётчики, `LoadStats` | для проверки — да | `test_clickhouse.py:29-36` |
| **1** | Транспортные однострочники (4 правки, все S) | да | нет |
| **2** | Сжатие тела (сжимать самим!) + прощупывание | да | `test_clickhouse.py:312` |
| **3** | `df.to_json` вместо построчного цикла | нет | ~6 тестов в `test_pandas_loader.py` |
| **3b** | `dtype=str` + пробелы в заголовке — **правка корректности** | нет | новые тесты |
| **4** | Диагностика падения при росте batch | да | нет |
| **5** | Конвейер + опциональная запись в шарды | да | 4 теста параллельной загрузки |
| **6** | Схема и DDL — **сначала два блокера** | нет | пины `UInt64` |
| **7** | Корректность данных | частично | новые тесты |
| **8** | Эргономика | нет | `test_app_state.py` целиком |
| **9** | Мёртвый код | нет | `test_csv_reader.py` удаляется |

Фазы 3, 3b, 6, 8, 9 можно делать без доступа к кластеру. Фазы 0, 1, 2, 4, 5 требуют прогона на
живом контуре для подтверждения — но написать и покрыть тестами их можно заранее.

**Минимальное подмножество, если нужен результат быстро:** 0 → 2 → 3. Фаза 0 даёт измерения,
фаза 2 — главный выигрыш по байтам, фаза 3 снимает CPU-потолок.

## 4. Правила репозитория, обязательные к соблюдению

Из `AGENTS.codex.md`:

- **Минимальный диф.** Наименьшее изменение, решающее задачу.
- **Явное лучше неявного:** аннотации типов, понятные имена, никакой магии.
- **Падать громко:** поднимать конкретные исключения с контекстом, не глотать ошибки молча.
- **Удаляем — значит удаляем.** Если задача говорит «убрать», старый код должен исчезнуть вместе с
  тестами. Никаких шимов совместимости для внутреннего кода. Проверять удаление механически — grep
  по удалённому символу.
- **`pathlib.Path` вместо `os.path`.** Dataclass вместо сырых словарей.
- Перед завершением — `/review` на итоговом дифе либо критическое перечитывание.
- **Проходящие тесты необходимы, но недостаточны:** перечитать критерии приёмки и убедиться, что
  выполнено структурное требование, а не только поведенческое.

Отдельно про этот репозиторий:

- DDL **без завершающей точки с запятой** — HTTP-драйвер не принимает multi-statement.
- Не возвращать глобальные дефолты для `ORDER BY` и ключа шардирования (`rand()`, `sipHash64(ID)`) —
  это прямо запрещено тестами `test_app_state.py:143-145`.
- ⚠️ **`tests/test_app_state.py` — это 24 сопоставления исходника с литералами, а не поведенческие
  тесты.** Любое переименование функции ломает их, не меняя поведения. Обновлять пины синхронно и
  осознанно, а не подгонять код под тест.

## 5. Какую задачу кому отдавать

Атомарные и механические задачи — лёгким агентам. Проектные решения — не отдавать.

| Тип задачи | Кому | Почему |
|---|---|---|
| «Где определено X», «что вызывает Y», «все использования Z» | `caveman:cavecrew-investigator` | read-only, отдаёт таблицу `file:line`, сжатый вывод |
| Точечная правка в 1–2 файлах: переименование, замена вызова, удаление функции | `caveman:cavecrew-builder` | отказывается от задач на 3+ файла, что здесь плюс |
| Ревью готового дифа перед коммитом | `caveman:cavecrew-reviewer` | одна строка на находку, без похвал и расширения скоупа |
| Широкий поиск по незнакомой области | `Explore` | fan-out, отдаёт вывод, а не дампы файлов |
| Многошаговая задача внутри одной фазы | `general-purpose` | |
| Проектные решения, выбор между подходами, правка плана | **никому, делать самому** | это то, где субагент даст правдоподобный, но неверный ответ |

Скиллы по фазам:

- `superpowers:executing-plans` — рамка исполнения плана. Вызвать до начала работ.
- `superpowers:test-driven-development` — для фаз 3, 3b, 6, 7, где есть проверяемое поведение.
- `superpowers:subagent-driven-development` — когда фаза разбивается на независимые атомарные куски.
- `superpowers:requesting-code-review` и `superpowers:verification-before-completion` — перед
  закрытием каждой фазы.
- `clickhouse:clickhouse-best-practices` — обязательно для фазы 6 (схема и DDL).
- `ponytail:ponytail-review` — для фазы 9 (мёртвый код) и как фильтр против переусложнения в любой
  фазе.
- `superpowers:using-git-worktrees` — если фазы делаются параллельно.

## 6. Верификация

После каждой фазы:

```bash
uv run --extra dev pytest
```

Критерий приёмки фазы 3 — новый сериализатор даёт **идентичный набор распарсенных JSON-объектов**
(сравнивать `json.loads`, не байты: `to_json` не ставит пробел после `:`), с единственным
задокументированным исключением на разделитель в `DateTime`.

Бенчмарк до/после — новый файл `benchmarks/serialize_bench.py`, печатает МБ/с старого и нового пути
плюс коэффициент сжатия.

На живом контуре — порядок проверок в разделе «Верификация» плана. Первым делом там `ping` до
кластера в покое и под нагрузкой: две команды, ноль кода, и они решают судьбу одной из четырёх
гипотез о канале.

## 7. Чего НЕ делать

Проверено и отвергнуто. Каждое всплывает в любом свежем анализе, поэтому список явный.

- **Native / `insert_df` / Arrow как основной путь.** Падает с HTTP 500 через этот прокси, включая
  вариант с `column_type_names`. Обоснование «типы не мапятся» при этом **неверно** — 13 из 18
  мапятся 1:1; настоящий блокер в невозможности проверить формат без живого доступа.
- **`ProcessPoolExecutor`** для сериализации — Windows `spawn` и pickle съедят выигрыш.
- **polars, orjson, shell-out в `clickhouse-client`** — `df.to_json` уже на C.
- **Реимплементация `sipHash64` на клиенте** — библиотеки нет, чистый Python слишком медленный.
- **Поднять `max_insert_payload_mb`** без сжатия — именно это и даёт «read limit is reached».
- **Передать `compression=` в `raw_insert` и считать, что тело сжалось.** Не сжалось: метод только
  ставит заголовок. Сжимать надо самим.
