# VERDICT ON BASELINE

THE SPLIT SURVIVES. Neither full-scan schema inference nor strict preflight is a large hidden share of the 45 minutes, and the plan's phase ordering does NOT need to be reordered on account of the pre-insert phase.

Full-scan inference is genuinely expensive - measured 5.07 MiB/s = 201.9 s per GiB (3.4 min/GB, 7.5% of 2700 s) on a realistic 187 B/row 20-column bank-like file, i.e. 18.5x slower than the pure pandas read floor of 10.9 s/GiB - but it is structurally OUTSIDE the reported clock. It runs on the "Read CSV" form button (app.py:431 -> :483 -> `_apply_csv_path`:570 -> `_analyze_csv`:635-640), a different Streamlit rerun from the load, whereas `start = time.time()` sits at app.py:864 inside `_create_and_load` and `elapsed` is read at :986. It is also opt-in and not the default: the radio defaults to Fast sample (app.py:455-464, index=0, `SCHEMA_INFERENCE_SAMPLE`), and Fast sample measures 3.60 s on the same file. So inference enters the 45 minutes only if the operator both selected Full scan AND was quoting subjective wall clock rather than the app's own "Load finished: N rows in X sec" line - which is the one question worth asking them.

Strict preflight IS inside the clock and IS on by default (`strict_preflight: bool = True`, settings.py:33), but a 1 GB file takes the >50 MB branch (app.py:901-916), which validates `max(200_000, batch_size)` rows. Measured: 5.94 s for 200,000 rows (33,643 rows/s) = 0.22% of 2700 s; 29.23 s even at sample_rows=1,000,000 (1.08%). Negligible either way.

Total real in-clock contamination is preflight ~6 s + connect (one mTLS handshake plus three bootstrap round trips at client.py:196-231) + DDL (one clusterAllReplicas query plus TWO `_verify_table_exists_on_cluster` loops of 30 attempts x 1.0 s, clickhouse.py:186-201 called at :303 and :322, up to 58 s of pure sleep) = ~9 s best case to ~69 s worst = 0.33%-2.55% of the clock, all of it currently attributed to the wire. That is a bias to correct in Phase 0, not a reattribution that changes priorities.

BUT the 92% figure is still wrong, for two reasons in neither document, and both inflate the apparent wire term rather than the pre-insert term:

(1) The driver silently re-uploads the ENTIRE body once on ConnectionResetError/BrokenPipeError, sleeping 0.1 s and continuing, logging only at DEBUG (httpclient.py:602-617, `max_attempts = max(2, retries + 1)` = 2 on the insert path). Every such event double-counts ~15 MB as wire time invisibly, and the plan reads that as evidence for a narrow pipe. It also makes the plan's Phase 5 statement "ретраи блоков... сейчас их нет вообще" factually false.

(2) `server % = Sum(elapsed_ns) / wall_clock` can only ever measure the initiator's FRONT half. `raw_insert_batch` (clickhouse.py:351-363) passes no `settings=` and `get_client` passes none either, so `distributed_foreground_insert` keeps its server default of 0 and the HTTP 200 returns as soon as the .bin spool file is written. The shard-side ReplicatedMergeTree commit, Keeper block-number allocation, dedup lookup, part creation and replica fetch all happen after the response, on the background `DistributedAsyncInsertDirectoryQueue`. So a small `server %` does not license "остальное — провод", and the plan's ~4x could land as a 4x faster progress bar with unchanged time-to-data-availability.

Practical conclusion: fix the instrument before trusting the ratio - four separate clocks with `server %` computed against `insert_wall_s`, the DEBUG retry count, and two `system.distribution_queue` / `system.query_log` queries. Do not re-order phases because of schema inference or preflight; do re-order the *diagnosis* because the wire term is measured by subtraction from a contaminated minuend and the server term is structurally truncated. One caveat I could not close locally and that no measurement can substitute for: whether the 45-minute observation came from this machine at all. If it did not, none of the machine-level numbers here transfer and the baseline must be retaken on the real client.

## N6. The serialized bytes for a given source row are a function of batch_size - so 'retry with a smaller batch' silently writes different data, and every resume or dedup-token scheme the plan contemplates is unsound

- CONF: established
- CLAIM: `iter_pandas_chunks` calls `pd.read_csv` without `dtype=`, so pandas infers dtype PER CHUNK. ## N7. F74's remediation is backwards for Windows: the OS default reported to an application here is 64 KiB, four times SMALLER than the driver's pin - and the driver's option list contains SO_SNDBUF twice, so the receive buffer is never set at all

- LAYER: Windows Winsock defaults below Python (the comparison value F74 needs does not exist in any source file)
- CONF: likely
- CLAIM: Inventory finding #4 (F74) and the plan's 'Главная неизвестная' table both rest on the premise that the hardcoded SO_SNDBUF=256 KiB is SMALLER than what Windows would have used, and F74's remediation is 'отфильтровать SO_SNDBUF из core_socket_options и добавить больший размер'. Separately, and independent of any OS question, `core_socket_options` lists `(SOL_SOCKET, SO_SNDBUF, 1024*256)` TWICE on consecutive lines - a copy-paste defect where the second entry was almost certainly meant to be SO_RCVBUF. # CLEAN LAYERS

- Client local storage, NTFS readahead and antivirus. Measured on the client: 1 GiB reads at 3922 MB/s uncached (FILE_FLAG_NO_BUFFERING), and pandas parses a 1 GiB CSV at 114 MB/s / 802,000 rows/s through the exact read path the app uses. Observed app throughput is 380 KB/s / ~1,900 rows/s, so disk is ~10,000x and CSV parse ~420x faster than needed. Endpoint security and network filtering were measured and excluded as a cause: real-time protection is on with no measurable cost on this path, and no socket-layer inspection is active. Independently corroborates the plan's 'client CPU is 7-9%' premise from a direction the plan did not use.
- TLS record layer, mTLS crypto and Nagle. OpenSSL emits at most 16384 bytes of plaintext per record, so a 14.7 MB body becomes 898 records and TLS 1.3 framing overhead is 19,756 B = 0.134% of the body. Measured the same 14.7 MB through a real TLS 1.3 socket (TLS_AES_256_GCM_SHA384) with TCP_NODELAY and SO_SNDBUF=256 KiB set exactly as the driver sets them: 0.018 s = 815 MB/s, i.e. ~0.2% of the ~9 s per block the observed throughput implies. `TCP_NODELAY = 1` is already in core_socket_options (httputil.py:39) so Nagle is off on every socket, and delayed ACK cannot throttle a bulk unidirectional send. Worth recording because TLS is the most plausible-sounding remaining suspect once compression lands and the wire is still slow.
- Strict preflight as a large share of the 45 minutes. It IS inside the load clock and it IS on by default (settings.py:33), but a 1 GB file takes the >50 MB branch, which validates `max(200_000, batch_size)` rows: measured 5.94 s for 200,000 rows (33,643 rows/s) = 0.22% of 2700 s, and 29.23 s even if batch_size were 1,000,000 (1.08%). Real, worth timing separately in Phase 0, but not a hidden term.
- Per-packet ceilings on the network path. At 380 KB/s with MSS 1228 the client is sending only ~309 packets/s, which eliminates VPN crypto throughput, wireless airtime, and firewall/NAT packets-per-second limits as candidate explanations. Windows TCP configuration is also unremarkable: CUBIC, IW10, HyStart on, pacing off, RFC1323 timestamps enabled, receive-window auto-tuning normal.
- Hybrid-CPU scheduling and power throttling. This Windows build has no Thread Director support for the client's hybrid CPU, which is a real concern in principle, but it is refuted for this workload by the healthy 114 MB/s parse rate measured on a desktop-class part under the Balanced power scheme - not a power-limited laptop.
- SQL construction in the cluster-existence checks. I suspected a real bug here: `_existing_target_tables` and `_table_exists_on_cluster` pass identifiers through `quote_identifier()` and then interpolate the result into single-quoted string literals (`WHERE database = '{database}'`), which would compare against backtick-wrapped text and never match, silently disabling both the ExistingTableError guard and the partial-state branch. It is not a bug: clickhouse.py:61-64 shows `quote_identifier` is a VALIDATOR, not a quoter - it returns the identifier unchanged if it matches `[A-Za-z_][A-Za-z0-9_]*` and raises otherwise. The comparisons are correct as written.
- Type-conversion correctness of the `to_json` path relative to the current serializer. Independently re-confirmed that both the current per-row serializer and the Phase 3 to_json path emit `null` for the NaN that `_convert_series` produces for Nullable(String), with byte-compared parsed JSON objects identical including on Cyrillic data. The pandas 3.0 None-to-NaN coercion at pandas_loader.py:686 is an implementation trap for the Phase 3b author, not live corruption today.
