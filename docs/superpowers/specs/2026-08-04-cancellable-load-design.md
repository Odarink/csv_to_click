# Загрузка, которую видно, которую можно остановить и о которой остаётся правда

Дата: 2026-08-04. Часть C из трёх; A — установка и запуск, B — шаги
интерфейса (обе сделаны и влиты в `main`).

## Кому и зачем

Те же 2–10 аналитиков на Windows. Заливка их файлов идёт десятки минут.
Успех: случайный клик или F5 не убивает часовую загрузку; передумал — остановил
кнопкой и знает, что стало с таблицами; на файле любого размера видно, сколько
прочитано; итог не исчезает с экрана; присланный JSON прогона отвечает на
вопросы «что с таблицами» и «кто был узким местом» без ручной арифметики.

## Что сейчас ломается

1. **Загрузку нельзя отменить, а rerun её убивает.** Продюсер живёт на потоке
   скрипта Streamlit внутри `_create_and_load`; каждый `st.*`-вызов может
   бросить `RerunException`. Отсюда троттлинг `LOAD_UI_MIN_INTERVAL_S` —
   лечение симптома, а не причины.
2. **Прогресс-бар мёртв для файлов больше 50 МБ.** Доля считается от
   `total_rows`, а он известен только после полной строгой проверки, которая
   на больших файлах заменяется выборочной. Общее число строк неизвестно —
   а размер файла в байтах известен всегда.
3. **Итог загрузки исчезает после перерисовки.** Финальные строки живут в
   `st.empty()`-слотах; любой rerun оставляет пустой экран, и поля 0b/8a
   видны только в JSON-записи.
4. **Запись прогона не говорит, что стало с таблицами.** После `514466c`
   исходов два — «удалены как пустые» и «оставлены с данными», — и оператор
   из присланного файла их не различает.
5. **Производные приборы 0b не попадают в запись.** Пишется только
   `server_share`, который при нескольких воркерах всегда `null`;
   `worker_occupancy` и `server_share_of_insert` считались вручную.

## Решение

### 1. Загрузка уезжает с потока скрипта в LoadJob

Новый модуль `src/csv_click/load_job.py`, в котором **нет ни одного
обращения к Streamlit** (закреплено тестом на импорты):

- `LoadJob` держит `threading.Thread` и `threading.Event` **композицией**, не
  наследованием: поле `_stop` в наследнике Thread ломает `join()` и
  `is_alive()` (ловушка из `memory/csv-click-library-traps.md`).
- Тело работы — сегодняшняя `_create_and_load` с вырезанными `st.*`:
  preflight → connect → DDL → загрузка → судьба таблиц → запись прогона.
  Порядок фаз, тексты сообщений и ветки исключений сохраняются, чтобы диф
  читался против `git show HEAD`.
- Лог — список строк под локом; текущая фаза, счётчики (`LoadStats`),
  исход, судьба таблиц, путь записи — поля задачи. Писатель у счётчиков
  один (поток задачи), интерфейс их только читает.
- Реестр «одна активная задача на процесс» живёт в `load_job.py`, а не в
  `app.py`: Streamlit пере-исполняет сам скрипт на каждом прогоне, и его
  глобалы не переживают rerun; импортированный модуль — переживает.
  Пока задача жива, второй старт не разрешается — сегодня двойной клик
  может запустить две заливки в одну таблицу. Побочный выигрыш: после F5
  новая сессия видит ту же задачу, и загрузка переживает обновление страницы.
- Всё, что трогает `st.session_state`, делается на потоке скрипта ДО старта:
  подбор effective_read_options, маппинги из редактора, `RunConfig`.
- Поток — daemon: закрытие процесса Streamlit убивает загрузку, ровно как
  сегодня. Запись прогона в этом случае теряется — тоже как сегодня.

### 2. Отмена

- Кнопка **Cancel load** взводит `Event`; загрузчик получает
  `cancel_callback` (тот же контракт, что у `analyze_csv_with_pandas_chunks`)
  и проверяет его между чанками и между блоками на обоих путях —
  последовательном и параллельном.
- Отмена поднимает новый `CsvLoadCancelled` (в `errors.py`, наследник
  `CsvClickError`). На параллельном пути уже отданные воркерам блоки
  дорабатывают через существующий `cancel_pending`: подтверждённые
  засчитываются, неотправленные идут в `blocks_unconfirmed`.
- Отмена не мгновенная: блоки в полёте доедут (секунды), во время
  connect/DDL сработает на границе фаз. Кнопка после нажатия говорит
  «Cancelling…».
- `outcome` в записи — новый `"cancelled"`. Судьба таблиц — по той же
  логике, что при сбое (`514466c`): есть подтверждённые блоки → оставить с
  данными и сказать об этом; нет → удалить как пустые.

### 3. Живой прогресс по прочитанным байтам

- `iter_pandas_chunks` получает необязательный `on_bytes_read`: счётчик-обёртка
  над бинарным файлом отдаётся `pd.read_csv`, после каждого чанка наружу
  уходит накопленное число байт. Снято зондом на pandas 3.0.3: байты растут
  постепенно (буфер упреждающего чтения ~3,4 МБ), монотонно, финал равен
  размеру файла байт в байт; кодировка поверх бинарной обёртки работает.
- Новое поле `LoadStats.src_read_bytes`; доля = `src_read_bytes / src_bytes`.
- Подпись говорит явно: это **прочитано из файла**, а не подтверждено
  сервером — рядом счётчик вставленных строк. Чтение опережает вставку на
  блоки в полёте и буфер, и прятать это нечестно.

### 4. Опрос из интерфейса

- Пока задача жива, прогресс рисует `st.fragment(run_every=1.0)`: фаза,
  полоса по байтам, вставленные строки, хвост лога
  (`LOAD_LOG_TAIL_LINES`), кнопка Cancel. Зонд подтвердил: фрагмент есть в
  Streamlit 1.58, AppTest видит его содержимое, кнопка внутри кликается.
- Клик по кнопке внутри фрагмента перерисовывает только фрагмент; когда
  задача закончилась, фрагмент делает один полный `st.rerun()`, и итог
  рисуется обычным путём.
- Троттлинг `LOAD_UI_MIN_INTERVAL_S` и `ui_due` удаляются вместе со своими
  тестами: интерфейс больше не пишется из загрузки — он сам читает задачу
  раз в секунду.

### 5. Итог, переживающий перерисовку

- Итог рисуется **на каждом прогоне** из состояния завершённой задачи в
  реестре: успех/ошибка/отмена, строки `format_load_stats_lines`, судьба
  таблиц, путь записи, полный лог в expander. `st.empty()`-слоты для итога
  не используются.
- Итог стоит, пока оператор не начал новую загрузку — она заменяет задачу
  в реестре.

### 6. Запись прогона: судьба таблиц и производные приборы

- В записи появляется блок `tables`: оба имени (`distributed`, `local`) и
  `fate` — одно из:
  - `not_created` — сбой до DDL, таблиц наших нет;
  - `created` — успех (или сбой одного лишь отчёта после успеха): обе
    таблицы на месте со всеми данными;
  - `kept_with_data` — сбой или отмена после подтверждённых блоков,
    таблицы оставлены;
  - `dropped_as_empty` — сбой или отмена без подтверждённых блоков,
    таблицы удалены;
  - `cleanup_failed` — удалить пытались, не вышло: таблицы, скорее всего,
    остались, ошибка в логе.
  `_handle_tables_after_failed_load` переезжает в `load_job.py` и
  **возвращает** fate вместо того, чтобы только логировать.
- `write_run_record` дописывает в `stats` три производных прибора:
  `worker_occupancy`, `server_share_of_insert`, `producer_unattributed_s` —
  те самые три строки из передачи. `src_read_bytes` попадает через `asdict`.
- Ветка `interrupted` остаётся страховкой от неожиданного `BaseException`,
  но штатно недостижима: в теле задачи нет `st.*`, бросать `RerunException`
  некому.

## Проверяемость

| Что проверяется | Как |
|---|---|
| В load_job нет Streamlit | тест исполнением: подпроцесс импортирует `csv_click.load_job` и проверяет, что `streamlit` не появился в `sys.modules` |
| Отмена останавливает оба пути | fake-клиент, cancel после N блоков → `CsvLoadCancelled`, подтверждённые блоки в stats, неотправленные в `blocks_unconfirmed` |
| Судьба таблиц в записи | пять исходов fate, каждый своим сценарием |
| Прогресс по байтам | `on_bytes_read` монотонен, финал = размеру файла; `src_read_bytes` в stats и в записи |
| Прогресс и Cancel на экране при живой задаче | AppTest с подставной задачей |
| Итог переживает rerun | AppTest: завершить задачу, сделать ДОПОЛНИТЕЛЬНЫЙ `at.run()`, итог всё ещё виден |
| Второй старт при живой задаче не проходит | AppTest: предупреждение, задача в реестре та же |
| Производные приборы в записи | присутствуют, включая null-случаи |
| README не разошёлся с кнопками | существующий `test_readme_matches_the_app` (дополнить README) |

Метод как в A и B: тест первым с фактом, снятым исполнением; мутационная
проверка с гашением кэша байткода и восстановлением всех тронутых файлов;
состязательное ревью финального дифа через Workflow с линзой
`regression_of_this_diff`. Отвергнутые решения закрепляются мутацией.

## Границы

Не входит:

- **отмена preflight-валидации** — на рабочем профиле это секунды
  (выборка 200 тыс. строк), а полная проверка бывает только у файлов < 50 МБ;
- **реаттач к загрузке после закрытия процесса Streamlit** — поток умирает
  с процессом, как и сегодня;
- **прогресс подтверждённых сервером байт** — только прочитанные из файла,
  и подпись говорит об этом;
- **возврат к скорости и параллельные продюсеры** — решение оператора
  (раздел 2 передачи), сюда не входит.

## Риски

- **`st.*` из чужого потока Streamlit молча не работает.** Закрыто
  конструктивно: в модуле задачи Streamlit не импортируется, и это держит
  тест.
- **Таймер фрагмента в AppTest не тикает.** Тесты дёргают `at.run()` руками;
  поведение фрагмента снято зондом до дизайна, а не предположено.
- **Реестр на процесс переживает тесты.** Автосброс фикстурой между тестами.
- **Две сессии одного процесса видят одну задачу.** Приложение по замыслу
  однопользовательское (launcher поднимает свой порт на машине оператора);
  для второй вкладки того же оператора общая задача — поведение желаемое.
- **Счётчики читаются без лока.** Писатель один — поток задачи; интерфейс
  читает целые числа, атомарные под GIL. Рассинхрон на долю секунды
  допустим и виден только как чуть отстающая цифра.
